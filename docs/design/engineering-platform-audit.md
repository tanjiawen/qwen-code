# 工程编程平台能力审计报告（人话版）

- 日期：2026-08-07
- 审计对象：qwen-code 库 `main@5be1c19fe`（v0.21.5-study.7）
- 一句话：**方向都对，但"铁打做到的"和"写在纸上的"要分清**

## 这份报告在回答什么问题

我们最近把**代码审查**（OpenCodeReview，简称 OCR）做成一个独立的小助手，加进了这个开发工具。问题来了：加上它之后，这个工具是不是就够格当一个**完整的开发平台**了？

一个完整的开发平台，至少得会干 6 件事：

1. **看懂需求**（分析）—— 先别急着写码，把"你到底要啥"问清楚
2. **拆解问题**（拆解）—— 把大活拆成小模块，定好每个模块的边界
3. **写代码**（编程）—— 按拆好的结构填实现
4. **管住流程**（控制）—— 先后顺序得对，不能跳步
5. **检查质量**（检查）—— 写完要验，改完要审
6. **产出靠谱代码**（稳）—— 尽量不出错、不埋雷

## 咱们现在用什么办法保证这 6 件事

办法分三个层次，**靠谱程度不一样**，这个必须分清：

| 层次       | 打个比方                                   | 靠谱吗                      |
| ---------- | ------------------------------------------ | --------------------------- |
| **硬闸门** | 收费站栏杆，**不过不让走**                 | 铁打属实，AI 想跳也跳不掉   |
| **靠自觉** | 交通规则，白纸黑字写着，但得靠开车的人自觉 | 写了，但 AI 可能偷懒/装样子 |
| **人工喊** | 得有人想起来，主动叫它去做                 | 最不牢靠，忘了就没了        |

对应的具体东西：

- **硬闸门**：几个"检查员"脚本（Stop 时自动跑）。改了代码但没通过编译 / 没跑过测试 / 没做代码审查 → 直接拦下，不许收工。
- **靠自觉**：写在流程规则里的要求，比如"先写测试再写代码""验证通过才能说完成了"。AI 通常照做，但没强制。
- **人工喊**：`ocr-review`（代码审查小助手）、`test-engineer`（测试小助手）——得主任务主动派人去叫它们。

## 6 件事到底落实了没

| 那件事       | 靠什么                                            | 落实程度                        | 人话点评                                  |
| ------------ | ------------------------------------------------- | ------------------------------- | ----------------------------------------- |
| 看懂需求     | 一个"拷问"小助手（grill-me）+ 统一术语表 + 先调研 | ✅ 流程强制作了                 | 流程靠谱；但问得深不深，看 AI 水平        |
| 拆解问题     | 拆模块 + 定接口 + 写设计文档                      | ⚠️ 流程写了，但没法硬查         | "要拆、要定接口"是规则，AI 可能打个马虎眼 |
| 写代码       | 定好接口后填实现                                  | ✅ 流程强制作了                 | 顺序管住了                                |
| 管住流程     | 流程顺序 + 硬闸门                                 | ✅ 硬性管住                     | 顺序错了会被拦                            |
| 检查质量     | 写测试 + 验证 + 编译/测试闸门 + 代码审查          | ✅ 局部硬性                     | 编译、测试、审查都被硬拦；但见下面的短板  |
| 产出靠谱代码 | 编译通过 + 跑过测试 + 审查过                      | ⚠️ 只保证"跑过"，不保证"跑得对" | 最关键的短板，见下                        |

## 最实在的短板（不藏着掖着）

**1. 测试闸门只查"跑没跑"，查不了"跑得对不对"。**
闸门能拦住"没跑测试"，但拦不住"测试写得烂"。比如：代码逻辑错了但能编译、测试全绿但断言是糊弄的——照样放行。**这是最要命的一条**，也是这类工具的天然边界。

**2. "靠自觉"的几条规则，AI 可能装样子。**
"先写测试""验证过了再说完成"这些，没有硬闸门兜底，AI 真想糊弄也糊弄得了。

**3. 缺"真的把程序跑起来看"这一关。**
现在靠编译 + 单测 + 审查，但"真刀真枪跑一遍看行为对不对"没做成硬闸门，靠 AI 自觉。

**4. 拆解这一步没有硬性地"先定接口再动手"。**
"要拆解、要定接口"是规则，但没有工具强制检查"你确实先定了接口才写代码"。

## 下一步能改啥（按划算程度排）

1. **查测试是不是真覆盖了改动**：改了哪个文件，就检查有没有对应的测试文件（而不是只查"跑过没"）。这是最值的一改。
2. **把"验证"从靠自觉升级成硬闸门**：验证命令真的跑过才算数。
3. **把"真跑一遍程序"做成硬闸门**。
4. **强制"先定接口再写代码"**，把接口声明变成能检查的产物。
