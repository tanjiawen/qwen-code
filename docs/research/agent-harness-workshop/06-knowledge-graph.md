## 核心理念

### 知识图谱在 Agent 系统中的定位

海致科技的核心技术主张可以用一个比喻概括：**知识图谱是"左脑"，大模型是"右脑"**。

- **知识图谱**（左脑）：存储结构化的、显式的事实知识，提供严格的逻辑推理和可解释性。在政务、公安等场景中，这意味着每一条推理链路都可以追溯、可以审计。
- **大模型**（右脑）：提供快速的语言理解、泛化能力和生成能力，但本质上是黑盒，容易产生"幻觉"（hallucination），缺乏对事实知识的可靠访问。

两者的融合目标是：**用知识图谱的刚性约束来驯服大模型的不确定性**，使 Agent 在关键行业场景中"更准确、更高效、更可信、更合规"。

### 与纯向量检索（RAG）的区别

当前主流的 RAG（Retrieval-Augmented Generation）方案基于向量相似度检索文本片段，存在几个结构性局限：

| 维度         | 向量 RAG                     | 知识图谱增强                                   |
| ------------ | ---------------------------- | ---------------------------------------------- |
| 检索单元     | 文本片段（chunk）            | 实体、关系、社区及其摘要                       |
| 索引结构     | 向量相似度索引               | 图结构知识索引                                 |
| 擅长问题     | 局部事实查询（"X 是什么？"） | 全局语义理解（"这个数据集的主要主题是什么？"） |
| 多跳推理     | 弱——需要多次检索拼接         | 强——沿图的边自然遍历                           |
| 可解释性     | 低——返回的是相似文本         | 高——返回的是结构化推理路径                     |
| 行业逻辑约束 | 无法表达                     | 可以通过本体和规则硬编码                       |

Microsoft 的 GraphRAG 研究（arXiv:2404.16130, 2024）验证了这一点：在百万 token 级别的语料上，GraphRAG 通过构建实体知识图谱 → 社区发现 → 社区摘要的流水线，在全局性问题的回答质量上显著优于传统向量 RAG。

### 为什么 Agent 需要结构化外部记忆？

Stanford 的 Generative Agents 研究（arXiv:2304.03442, 2023）展示了 LLM Agent 的记忆架构：自然语言记忆流 → 检索 → 反思 → 规划。但这个架构的记忆是非结构化的——它是一堆自然语言条目的集合，缺乏实体间的显式关联。

知识图谱作为 Agent 外部记忆的优势：

1. **关系显式化**：Agent 不需要从文本中"猜"两个实体之间的关系，图上直接有边。
2. **推理可追溯**：每一步推理都对应图上的一条路径，可以回溯和审计。
3. **增量更新**：新知识以三元组（实体-关系-实体）的形式插入，不需要重建整个索引。
4. **约束传播**：本体（ontology）定义的约束可以自动检查一致性，防止 Agent 产生逻辑矛盾。

## 技术方案

### 海致科技的技术体系

海致科技的技术栈围绕三个层次展开：

#### 1. 底层：自主可控的图计算引擎

- 海致星图（Haizhi Xingtu）是海致科技的全资子公司，专注知识图谱和图数据库技术。
- 攻克了分布式一致性协议等关键技术，开发了支持大规模实时图计算的国产数据库系统。
- 获得 2021 年 CCF 科技进步卓越奖。
- 2021 年建立"海致高性能图计算院士专家工作站"，首席科学家为中国工程院院士、清华大学郑纬民教授。
- 近年专利布局（2026 年公开）：知识图谱领域知识库检索和图谱分析、知识图谱海量数据图查询、基于指定关系类型的知识图谱实体融合、基于知识图谱链路追踪、基于知识图谱实体和关系的排序。

#### 2. 中间层：图模融合（Graph-Model Fusion）

2023 年 9 月，郑纬民院士在北京发布了 **Atlas LLM 知识图谱与大模型融合应用平台**。这是海致科技的核心产品，技术架构围绕三个环节：

- **知识映射（Knowledge Mapping）**：将行业数据和已有知识资产映射为结构化的知识图谱，作为大模型的外部知识源。
- **知识校验（Knowledge Verification）**：用知识图谱中的事实知识校验大模型的输出，识别和纠正幻觉。
- **知识优化（Knowledge Optimization）**：将大模型的输出反馈到知识图谱中，实现知识的增量更新和质量提升。

关键特性：

- 支持灵活切换不同的开源大模型，降低部署成本。
- 避免重复建设数据/知识体系，复用客户已有的数据资产。
- 面向 B 端企业级用户。

#### 3. 上层：产业级智能体

海致科技的最终目标是通过图模融合技术开发"产业级智能体"，为行业客户提供端到端的 AI 解决方案。

### 院士工作站的前沿方向（2026 年升级）

2026 年 7 月，海致院士专家工作站经北京市科协批准，从"高性能图计算"战略升级为"知识图谱 + 大模型融合"方向。新的研究重点：

1. **大规模分布式系统与高性能计算**
2. **知识图谱与大模型融合**
3. **基于"GNN + LLM"交互的新型大模型框架**——将图神经网络（GNN）的结构化表示能力与 LLM 的语言理解能力结合
4. **可信大模型应用的核心底层技术**
5. **自主可控图数据库技术与国产软硬件生态**

### 学术界的理论框架

IEEE TKDE 2024 发表的综述论文《Unifying Large Language Models and Knowledge Graphs: A Roadmap》（arXiv:2306.08302）提出了 LLM + KG 统一的三个框架，与海致科技的实践高度吻合：

| 框架                  | 含义                                   | 海致科技的对应                          |
| --------------------- | -------------------------------------- | --------------------------------------- |
| KG-enhanced LLMs      | 用知识图谱增强大模型的预训练和推理     | Atlas LLM 的知识校验环节                |
| LLM-augmented KGs     | 用大模型辅助知识图谱的构建、补全、问答 | Atlas LLM 的知识映射环节                |
| Synergized LLMs + KGs | LLM 和 KG 双向协作、互相增强           | Atlas LLM 的知识优化环节 + GNN+LLM 框架 |

## 行业实践

### 政务场景

海致科技的 Atlas LLM 平台已在政务场景中部署。政务场景对 Agent + 知识图谱的需求特征：

- **政策知识图谱**：将法规、政策文件、行政流程结构化为知识图谱，Agent 在回答市民咨询时必须严格依据政策条文，不能"自由发挥"。
- **跨部门数据关联**：政务数据分散在多个部门，知识图谱可以将不同来源的实体（人、机构、事项、地址）关联起来，支持跨部门的协同查询。
- **合规性约束**：政务场景对输出的合规性要求极高，知识图谱提供的刚性逻辑约束是纯向量 RAG 无法满足的。

### 公安场景

公安场景是海致科技的重点行业之一（虽然官网未显式列出，但任务背景和行业报道均确认）。典型应用：

- **案件关联分析**：将人员、地点、事件、物证等构建为知识图谱，Agent 可以沿图的边进行多跳推理，发现隐藏的关联关系。
- **情报研判**：从海量非结构化情报文本中，用 LLM 抽取实体和关系，自动构建和扩展知识图谱（LLM-augmented KG）。
- **链路追踪**：海致星图 2026 年获得的"基于知识图谱链路追踪方法"专利，直接对应公安场景中的资金链、通信链、关系链追踪需求。
- **实体融合**：同一嫌疑人可能在不同数据源中有不同的身份记录，"基于指定关系类型的知识图谱实体融合方法"专利解决的就是这个问题。

### 其他行业

海致科技的产品还覆盖：

- **金融**：风控知识图谱、反欺诈关联分析
- **能源**：电力设备知识图谱、供应链关联分析
- **智能制造**：工业知识图谱、设备故障推理
- **交通**：交通网络图谱、路径优化

## 与 qwen-code 的关联

### qwen-code 当前的记忆机制

qwen-code 目前使用文件系统做记忆：

- **MEMORY.md 索引** + 独立的 markdown 记忆文件（带 frontmatter 元数据）
- 按类型分类：user / feedback / project / reference
- 按作用域分离：用户级（跨项目）vs 项目级
- 检索方式：全量加载 MEMORY.md 索引到上下文，按需读取具体文件

这本质上是一个**非结构化的、基于文本的记忆系统**。它简单、透明、可审计，但缺乏实体间的显式关联。

### 知识图谱能带来什么改进？

| 当前文件系统记忆                          | 知识图谱增强方向                         |
| ----------------------------------------- | ---------------------------------------- |
| 记忆条目之间没有显式关联                  | 实体（人、项目、概念）之间有显式的关系边 |
| 检索靠索引文件的全量扫描                  | 可以沿图的边做多跳遍历，发现间接关联     |
| 无法表达"A 依赖 B""C 是 D 的子任务"等结构 | 关系类型可以精确表达依赖、层级、因果     |
| 增量更新靠手动维护索引                    | 三元组插入天然支持增量更新               |
| 无法做一致性检查                          | 本体约束可以自动检测矛盾                 |

### 适用场景判断

**知识图谱适合的场景**（qwen-code 可能受益）：

- 大型项目中，代码实体（模块、类、函数）之间的调用关系和依赖关系——这其实就是 codegraph 技能已经在做的事情
- 跨会话的项目知识积累：哪些决策导致了哪些架构选择，哪些 bug 与哪些模块相关
- 多人协作场景：谁负责什么模块，哪些 PR 涉及哪些文件

**知识图谱不适合的场景**（文件系统记忆已经够用）：

- 个人偏好和反馈记忆——这些是扁平的、少量的，不需要图结构
- 简单的参考链接——一个 markdown 列表足够
- 会话内的临时上下文——用 plan/todo 更合适

### 务实建议

对 qwen-code 来说，引入完整的知识图谱系统（图数据库 + 本体建模 + 图查询引擎）会显著增加复杂度，与" simplicity first"原则冲突。更务实的路径：

1. **已有的 codegraph 技能**（基于 neug 图数据库 + zvec 向量索引）已经在代码结构分析方向实现了知识图谱的核心价值。
2. **记忆系统**可以在现有 markdown 文件的基础上，增加轻量级的关系标注（例如在 frontmatter 中添加 `related: [file1.md, file2.md]` 字段），而不需要引入图数据库。
3. **GraphRAG 的思路**（从文档中抽取实体和关系 → 社区发现 → 社区摘要）可以作为记忆检索的增强手段，但实现成本较高，适合作为长期方向而非短期改进。

海致科技的实践给我们的核心启示是：**知识图谱的价值不在于替代文本，而在于提供文本无法表达的结构化约束和可追溯的推理路径**。对于 qwen-code 这样的开发者工具，代码结构图（已有）和项目决策图（潜在方向）是最有价值的知识图谱应用点。
